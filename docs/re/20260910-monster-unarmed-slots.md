# 怪物徒手取哪一件：那幾格根本沒被讀（2026-09-10）

證據等級 `已證實`。回答 RE-131 結尾留下的洞。

## 問題

RE-131 解出隊員那一側的徒手四式：`sub_26AC2` 依攻擊選項查 `0x0FD2`
（`00 50 60 00 40 10`）加 `0x100`，除以一格 `0x10` 得槽號，四式對上
FEET／SHIELD／HEAD／HANDS。同一份筆記在結尾留了一句：

> 怪物那一側沒接——同一張表加 `+0x30` 落在 `0x30`／`0x80`／`0x90`／`0x70`／`0x40`，
> 其中三個在怪物記錄的已知版面之外（武器 `+0x20`、護甲 `+0x30`／`+0x40`／`+0x50`、
> 盾牌 `+0x60`），還沒查那幾格是什麼。

這個洞不是紙上問題。怪物本體記錄的**步幅是 128**（`0xCD92 + (index-6)*0x80`，
RE-080 與 SPEC-017 一致），而 `+0x80`／`+0x90` 已經越過那一格的邊界——真要那樣取，
讀到的會是**下一隻怪物記錄的開頭**。而 remake 的 `NewQuest` 目前用
`unarmedFrom(monster.Worn)` 給怪物填了徒手武器，取的是 `monsters.json` 那份**母表**
的七格穿戴欄（母表記錄大得多，`+0x80`／`+0x90` 在它裡面確實有內容）。

兩者只可能有一邊對。

## 方法

靜態掃描回答不了這個問題——用算出來的指標取的存取在位元組層面看不見，掃到零筆
只證明沒有絕對定址的參考。所以改用 dosgolem 的讀取監看，讓原版自己說它讀了哪裡：
在本體記錄 `+0x20`…`+0xC0` 每一格填不同的可辨識值，開 `WatchReadsAt`，設好
「規劃過了（`+0x22`=1）、指令碼是徒手（`+0x25`=0x29）、這一式（`+0x23`）」再呼叫
`sub_26AC2(slot)`，看讀取落在哪幾格。

| 項目 | 值 |
|---|---|
| 輸入 | `KOLTOWN-unpacked.EXE`，SHA-256 `01f6f9a95c4adf8e9da59fa83bae57aa282e5576767b41bfc2f23302aeb9d1d2` |
| 位址空間 | IDA 線性；`sub_26AC2` = `0x26AC2` |
| 怪物本體記錄 | DS 相對 `0xCD92`，步幅 128 |
| 角色記錄 | DS 相對 `0xBB88`，步幅 `0x300`；穿戴欄自 `+0x100` 起 |
| 參戰者記錄 | DS 相對 `0x6712`，步幅 50；`+0x22` 規劃旗標、`+0x23` 攻擊選項、`+0x25` 指令碼 |
| 工具 | dosgolem `kol-oracle`（`5f9a9a1`）；`internal/oracle/monster_unarmed_probe_test.go` |

**正對照是這次的關鍵。** 只跑怪物那一側證明不了任何事：四式都只讀 `+0x20` 有兩種
可能——怪物那條路本來就只取武器（結論），或者設定根本沒讓它走進徒手分支（假陰性，
而且它安靜得跟成功一模一樣）。所以同一套設定也用在隊員身上，拿 RE-131 已解出的
答案當已知值。

## 結果

| 情境 | 讀到本體／角色記錄的哪幾格 |
|---|---|
| 怪物・有武器・選項 1／2／3／4 | 一律只有 `+0x20`（各 2 次） |
| 怪物・武器那格整格清零・選項 1／2／3／4 | 一律只有 `+0x20`（各 2 次） |
| 隊員・選項 1（踢） | 穿戴欄 `+0x50`（槽 5 FEET） |
| 隊員・選項 2（盾擊） | 穿戴欄 `+0x60`（槽 6 SHIELD） |
| 隊員・選項 3（頭槌） | 穿戴欄 `+0x00`（槽 0 HEAD） |
| 隊員・選項 4（拳） | 穿戴欄 `+0x40`（槽 4 HANDS） |

隊員那四式各自落在不同的槽，而且與 RE-131 的預測**逐項相符**——設定方式沒問題。
怪物那一側因此是真的：**沒有「徒手四式取穿戴品」這個機制**，`var_4` 一律指向本體
記錄 `+0x20`。把武器那一格整格清零（真正的赤手空拳）也不改變這件事。

RE-131 問的「那幾格是什麼」，答案是**那幾格根本沒被讀**。`+0x80`／`+0x90` 越過
128 的邊界這件事不會發生，因為原版從來不往那裡取。

## 對 remake 的意義

`internal/battle/state.go` 的 `NewQuest` 目前給怪物填
`UnarmedWeapon: unarmedFrom(monster.Worn)`，等於讓怪物的徒手四式各拿一件穿戴品去
算傷害骰——**原版不是這樣**。這是玩家看得見的差異（怪物徒手那幾手的傷害），
依專案規則屬於「會改變戰鬥數值的決定」，處置方式待使用者決定，本文件只固定證據。

`monsters.json` 的七格穿戴欄本身沒有錯：那是母表的內容，護甲三件
（`+0x30`／`+0x40`／`+0x50`）與盾牌（`+0x60`）都在戰鬥期記錄裡，仍然照常使用。
不成立的只有「怪物徒手時會去取那幾格」這個推論。
