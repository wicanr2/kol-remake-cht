# 正常玩家路徑收據

最新受阻打暈持物的正式回城保存與重載：[有限驗收](../blocked-stun-20261007.md)。
任務亂數的原型比較、壓縮證據及工作區清理：[保存入口](../retained-evidence.md)。
任務入口亂數接續的正式接線與驗收：[本輪入口](../quest-rng-20261007.md)。
既有長任務和其他收據保持各自的來源版本，不由此擴大原版或現行覆蓋。

這裡的截圖序列由 `cmd/kol` 的操作腳本產生，經過各畫面自己的狀態機——沒有
direct-entry、沒有座標注入、沒有測試旗標。輸入 token 對應原版鍵位：
`L R U D` 是方向鍵、`A S Z X` 是參考卡的斜走鍵、`<` `>` 移動圖示列白框、`RET` 執行、
`SPACE` 翻下一段文字。

短路徑（十幾二十步）逐步存圖，用 `verify_player_path.py` 驗；
從標題走到存檔的長路徑有上千步，改存**狀態軌跡**加幾張檢查點截圖，
用 `verify_full_path.py` 驗。

```
tools/run_kol_shots.sh workplace/play/path.spec
python3 tools/verify_player_path.py --plan docs/verification/player-path/town.json
python3 tools/verify_full_path.py   --plan docs/verification/player-path/full-chain.json
```

Python 工具必須在 Docker 內執行；以下命令均指容器內的工作樹。設 `KOL_BIN`
指定容器內已建置的遊戲後，重播與檢查器可直接使用它；重播會更新正式收據，
只核對回歸時使用 `check_player_paths.py`。
長路徑那幾份**從 plan 就能一鍵重生**：`tools/replay_player_path.py <名字>`（或 `--all`）
把腳本、種子、要讀的存檔與換過的資料檔組成規格檔跑一遍，再驗一次。
plan 因此要帶齊重跑所需的每一個旗標——`full-chain-ending` 的 `-quest-sites`
一度只寫在散文裡，改了戰鬥數值之後重跑打的是原版那十二隻 CYCLOPS，怎麼跑都跑不完。

## 收據與現行程式的對應

`verify_player_path.py` 與 `verify_full_path.py` **不重跑**，比的是收據目錄裡那幾張圖
與軌跡自不自洽，程式改了它們照樣通過。要抓回歸得重跑再比：`tools/check_player_paths.py`
重跑到 `workplace/replay-check/`，拿新的**狀態軌跡**與收據目錄裡的參考軌跡逐步比
（場景、位置與模式、提示、戰鬥階段與訊息、隊伍數值、結局），不寫回收據。
判準是機制一致，不要求畫面逐位元相同（2026-09-26 定案）：截圖差異只列出張數當參考。
短路徑的參考軌跡是 `<名字>/trace.json`，由 `--bootstrap` 從現行程式產生。
容器內設 `KOL_BIN` 使用已建置遊戲，`KOL_REPLAY_CHECK_DIR` 指向可寫輸出。全部檢查依
存檔依賴排序，續玩讀當輪新存檔；獨立輸入複製到輸出區，v1 匯入不寫回觀察來源。

```
python3 tools/check_player_paths.py --all
```

現行的做法：

- **讀檔開場**：`quest-take`、`quest-list`、`world-healer`、`full-chain`、
  `full-chain-reload`、`full-chain-ending` 都用 `-load` 直接在城裡開場。
  標題選角一律以名冊角色回到所在旅店（SPEC-016），存檔裡的隊伍與開場位置用不上；
  標題到旅店那一段由 `full` 驗。
- **種子**：野外每次時段變換都擲一次遭遇，天候重擲接在遭遇之前（SPEC-011 §1）。
  要驗的不是遭遇的路徑（`world-clock`、`world-quest`）依 SPEC-011 §9 從原種子往上
  逐一試、取第一顆路徑事件符合原設計的，試過的種子寫在 plan 描述。
- **受控亂數**：`world-healer` 要驗的就是治療那一條遭遇，`full-chain` 要一場打得贏的
  伏擊才接得上住宿存檔，`full-chain-ending` 要隊伍不帶傷走到最終任務地點（2026-09-27），三條以 `-ambush-rolls` 指定 `RollAmbush` 的前幾骰（plan 與
  收據都有 `ambush_rolls` 欄位），其餘亂數仍來自種子。依 CLAUDE.md「明示的受控亂數
  輸入」，使用者 2026-09-26、2026-09-27 決定。
- **自然事件照實走**：其他路徑路上擲到的伏擊、換日與治療照種子發生，戰鬥段由
  `tools/drive_battle_script.py` 依軌跡打出固定按鍵；打輸的也照實記錄。
- `flow-quest` 已撤下（見下）。

**改了戰鬥數值之後戰鬥那一段的按鍵就作廢了**（打幾個回合、每一手的訊息都不同）。
`tools/drive_battle_script.py` 用來重生它：跑一次腳本 → 讀軌跡的最後一筆 →
依規劃段停在哪一層決定下一批 token → 再跑，產出的仍是一串固定按鍵。走路與城裡
那幾段沿用原腳本的前後綴，只換中間那一段。

`docs/verification/battle-*/` 那幾份短收據同理，重跑用
`tools/replay_battle_receipts.py <名字>`（或 `--all`）：跑各自的 `replay.spec`，
再拿輸出的 PNG 對收據 `frames` 的 SHA-256 與版控裡那一張。

`verify_player_path.py` 檢查三件事：

1. 每一步的截圖存在、解得開、尺寸正確；
2. **相鄰兩步不得完全相同**——每個 token 都要有可見效果。
   這一條抓到過一個真的 bug：門口圖示列的白框位置沒有畫出來，
   按 `>` 之後畫面完全沒變；
3. 指定的檢查點與**已通過對拍**的截圖逐 byte 相同。

`verify_full_path.py` 檢查的是里程碑與檢查點：軌跡（`-trace` 寫出來的 JSON）在
指定的那幾步必須停在指定的畫面、座標與戰鬥階段，檢查點截圖必須與已對拍的那一批
逐 byte 相同，路徑寫出來的存檔必須逐欄對得上。軌跡是遊戲自己報的狀態，不是從畫面猜的。

### `quest-take`：接下一個任務

## `full`：從標題序列走到城鎮

`SPACE SPACE 5 D RET ESC D RET ESC D D D RET SPACE ESC 6 RET RET RET L R RET RET RET R D`，
27 張截圖。這條路徑由 `internal/flow` 串起來：它只決定「按了什麼鍵、畫面走到哪」，
每個畫面自己的狀態機維持原樣。

| 步 | 畫面 |
|---|---|
| 0–2 | 標題序列 → 書本封面 → 目錄頁 |
| 3–5 | 目錄頁 `5` → 角色選項 → 反白條移到 CREATE → New Character 頁 |
| 6–9 | ESC 回選項 → DELETE → 刪除清單 → ESC 回選項 |
| 10–14 | 反白條走過 EDIT PICTURE、EDIT SHIELD、HARBOR MASTER → 訊息頁 → 回選項 |
| 15–17 | ESC 回目錄頁 → `6` → 角色選擇清單 → 選領隊 → **旅店**進門敘述 |
| 18–19 | 店主招呼 → 白框在 DOOR → **戶外地圖** |
| 20–24 | 走離門口 → 走回（門口狀態）→ DOOR 進建築 → 招呼 → 出來 |
| 25–26 | 往東一步、往南一步 |

檢查點：第 21 步與門口對拍截圖、第 22 步與建築內部對拍截圖，都逐 byte 相同。

角色選項的 `EDIT PICTURE`、`EDIT SHIELD` 會被記進 `flow.Unimplemented`，
不會默默吞掉——測試盯著這一點。

## 這份收據不宣稱什麼

- 不宣稱可以從新遊戲一路玩到結局。接任務與回報各自走得通（`quest-take`、
  `full-chain` 那條路上的交付），但要在遊戲裡累積到 23 件仍然不現實，
  所以結局那一段的存檔是工具造的。`full-chain-ending` 證明的是
  「打完最終任務那一刻結局會出來」，不是「玩得到那一刻」。
- 長路徑從讀檔開場，不宣稱標題選角能接上存檔裡的隊伍；標題那一段只由 `full` 驗。
- 受控亂數那兩條（`world-healer`、`full-chain`）證明的是「擲到之後」的畫面與流程，
  不證明遭遇機率；機率由 RE-078／RE-112 與單元測試支撐。
- MOUTH 的輸入框已經做了，但**版面沒有對拍**：讀入上限與轉小寫有證據，
  游標的樣子與座標沒有。
- 不宣稱長路徑上的每一張畫面都與原版一致。六人隊伍的長路徑原版沒有取到對應的畫格；
  連上對拍證據的是 `world-quest` 那兩張，以及各段自己的短路徑收據。
- 戰鬥敗北之後的回寫依 SPEC-027 接上一部分，原版的完整返回路徑與額外掉落還沒驗；
  `full-chain-ending` 路上那一場敗北不宣稱與原版一致。
- 角色選項頁的 EDIT PICTURE／EDIT SHIELD 按下去不會轉場，只會記進未實作清單。
- 任務一覽只重畫抬頭那一層（`sub_16239`，RE-137，以原版法術一覽畫格佐證）；
  任務一覽本身沒有原版畫格，格子的座標與框的顏色有證據（RE-111）。
- 競技場的遭遇訊息與戰場地形都沒有對拍：原版在開打前把 `word_34968` 設成 1
  （走任務地點那一條），這一版照那個旗標推了訊息、地形則沿用隨機遭遇的逐格擲。
- 不宣稱鏡頭跟隨規則已證實。dead zone 是由 22 張原版畫格反解的**強推論**，
  規則本身沒有從程式碼讀出來。
