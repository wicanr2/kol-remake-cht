## 原版那一側

`tools/oracle/book_startup_test.go` 的 `KOL_BOOK_PLAN` 模式，seed=1、正常路徑，
按鍵序列 `.,Return,Return,.,.,Return,.,.,.,Return`。收據在
`workplace/battle-planning-20260911/`。

圖示列由畫面量得（起點 X=32、格距 32、Y 170..191），逐步是：

| 步 | 鍵 | 圖示列 | 白框 | 那一層是什麼 |
|---:|---|---:|---:|---|
| 入口 | — | 5 | 0 | 主指令列，行動者槽 1（Theodoric） |
| 0 | `.` | 5 | 1 | |
| 1 | Return | 2 | 0 | 選目標格（SPEC-010 mode 1） |
| 2 | Return | 6 | 0 | 攻擊式那一列 |
| 3–4 | `.` ×2 | 6 | 2 | |
| 5 | Return | 8 | 0 | 防禦方式那一列 |
| 6–8 | `.` ×3 | 8 | 3 | |
| 9 | Return | 5 | 0 | 寫回槽 1 |

寫回的值：`+0x23=1`、`+0x24=2`、`+0x25=0x29`。

三個都對得上 SPEC-010 §4 的換算：

| 值 | 算法 | 得數 |
|---|---|---:|
| 攻擊選項 `+0x23` | 徒手：圖號 − 0x36，第 2 格是 `0x37` | 1 |
| 防禦選項 `+0x24` | 圖號 − 0x2F，第 3 格是 `0x31` | 2 |
| 指令碼 `+0x25` | 主指令列第 1 格的圖號 | `0x29` |

`0x29` 是徒手，所以 6 格那一列是徒手攻擊式（`0x0F、0x2A、0x37…0x3A`）；
8 格那一列是防禦方式（`0x0F、0x2A、0x30…0x34、0x36`）——兩列的格數都與 SPEC-010
§4 的圖示清單相符。

## remake 那一側

同一份原版隊員資料與地形，`battle.NewQuest` 建場之後把規劃推到槽 1：

- 主指令列 `[0x7 0x29 0x16 0x27 0x5]`——5 格，第 1 格 `0x29`
- 攻擊式那一列 `[0xf 0x2a 0x37 0x38 0x39 0x3a]`——6 格
- 防禦方式 8 格
- 走同樣的位置（第 1 格 → 目標 → 攻擊式第 2 格 → 防禦式第 3 格）之後：
  `Command=0x29`、`Style=1`、`Guard=2`

## 比的是位置不是按鍵

原版收掃描碼、remake 收 token，輸入層不可能逐鍵對齊。可比的是**同一個位置代表
哪一格**：白框停在第 n 格時圖號是多少，以及那個圖號換算出來的三個值。按鍵只是
把白框搬到第 n 格的手段。

## 正反對照

把預期值改錯（主指令列 5→6、攻擊式 6→7、防禦選項 2→3）之後測試報錯，訊息列出
remake 的實際圖號。訊號拿掉會開口，不是恆真。

## 不宣稱

- 只比這一條路徑上的這一組選擇。其他指令（射擊、施法、移動、丟撿）與其他攻擊式／
  防禦式的格位沒有逐格走過。
- 攻擊結算、戰後回寫與保存鏈不在這一輪。
- 規劃期間 `DS:0x9E5A` 的語意仍未定案（見 worklist `planning-current-slot-semantics`）；
  這一支不依賴它——比較用的是槽號，不是那個位址。
