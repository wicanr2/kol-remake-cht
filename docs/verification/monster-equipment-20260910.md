# 怪物裝備能力：128 byte 三方比對（2026-09-10）

## 為什麼不必重新擷取

先前的收據記著「怪物記錄目前只擷取 `DS:CD92` 起 0x80 byte，不能當成全部穿戴欄已
完整保存」，於是這一項一直被當成「要先擴充擷取範圍」。**那句話有一半不成立**：

`0x80` 就是完整的一筆——`0xCD92 + (index-6)*0x80`（RE-080 與 SPEC-017 一致），
`TestMonsterTemplateCopyMatchesOriginal` 也用 `bodySize = 128`。護甲三件
（`+0x30`／`+0x40`／`+0x50`）、盾牌（`+0x60`）、技能（`+0x17`）、旗標（`+0x10`）、
撤退門檻（`+0x0D`／`+0x0E`）與金冠骰式（`+0x0F`）全都在這 128 byte 之內。

真正裝不下的只有母表 `worn` 的第 5、6 槽（`+0x80`／`+0x90`）——而那兩格原版在戰鬥中
根本不讀（[那幾格根本沒被讀](../re/20260910-monster-unarmed-slots.md)）。

所以資料本來就夠，缺的只是**沒有比**。

## 三方比對

`TestOriginalNormalMonsterEquipment`（`cmd/kol/original_monster_equipment_test.go`）：

1. **戰鬥期記錄的 bytes ↔ `monsters.json`**——母表抽取器讀對了沒。
2. **`monsters.json` ↔ remake 的 `Actor`**——適配器接對了沒。

SLEDGE 共 20 項通過：

| 項目 | 位移 |
|---|---|
| 旗標 | `+0x10` |
| 撤退門檻／恢復 | `+0x0D`／`+0x0E` |
| 金冠骰式 | `+0x0F` |
| 攻擊／招架技能（大端 16-bit） | `+0x17`／`+0x19` |
| 護甲重量（三件之和，空的不算） | `+0x30`／`+0x40`／`+0x50` 各 `+10` |
| 盾牌有無 | `+0x60` |
| 穿戴欄前五槽有無 | `+0x30`…`+0x7F` |
| `Actor` 的六個對應欄位＋盾牌等級 | — |

穿戴欄前五槽實得 3 件（Skull、Hide、Hide）；`worn[5]`（War Hammer）與 `worn[6]`
（Skull）在母表裡有內容但不在這 128 byte 裡，原版戰鬥中也不取它們。

## 判準踩過一次坑

第一版拿 `m.Worn[slot] != nil` 判斷「有沒有東西」，SLEDGE 的第 3、4 槽（原版是空的）
被判成不符。原因是 **`monsters.json` 的兩個欄位對「空」的約定不一樣**：

- `shield` 走 `item()`，整格全零回 `null`；
- `worn` 要保持七格對位，所以全零那幾格解出來是一個**每個欄位都是零的物件**，不是 `null`。

判準因此改成看記錄本身是不是整片零（`blankRecord`）。順帶確認 remake 沒有踩到同一個
坑：`cloneArmour` 只取前三格（`+0x30`／`+0x40`／`+0x50`），SLEDGE 那三格都有實料。

## 還沒做

規劃與攻擊結算的對拍。那需要原版在規劃入口**之後**的狀態快照，現有的三份都停在
規劃入口。
