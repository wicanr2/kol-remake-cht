# SPEC-020：規劃人物的檢視門檻生命週期

狀態：READY。日期：2026-09-08。授權以下已審查的規劃門檻生命週期實作；尚未 CONFORMED。

## 問題與證據

目前 `round.go` 的 BeginPlanning、EndTurn、AdvanceToParty 會跳過倒下人物，
沒有原版每個規劃位置的門檻擲骰與保存。即使未查看敵人，此差異也會改變後續亂數。
這是原版規則接線缺口，不能當作面板美化或只在 renderer 內補擲。

輸入 `KOLTOWN-unpacked.EXE`，SHA-256
`01f6f9a95c4adf8e9da59fa83bae57aa282e5576767b41bfc2f23302aeb9d1d2`。
IDA Pro 9.4 線性位址；證據與匯出工具見
[命令面板查核](../re/20260908-command-panel.md)。

原版資料流（已由 IDA 定位，完整生命週期待原版執行抽測）：

1. 0x1F05C..0x1F073：依排序位置取得人物，設定行動者與被檢視者索引。
2. 0x1F076..0x1F082：擲一次 1..100，保存 word_3B264。
3. 0x1F085..0x1F0D9：檢查不能行動／空位，必要時清招式及防禦後跳過。
4. 0x1F0DC..0x1F152：敵人走 AI；隊員走 0x1F155 起的互動規劃。
5. 0x1FAC4..0x1FAE7：標記已規劃、增加排序位置，下一位置回到步驟一。
6. 0x1FAC1 取消／返回跳到 0x1F16A，不重新經過步驟二。

## 待審查修正契約

- 每個實際被原版規劃迴圈走訪的位置，先擲並保存門檻，再檢查可否行動。
- 同一位置重複呼叫 AdvanceToParty、BeginTurn、切換面板、查看目標及取消，
  都不得增加這項亂數消耗；下一位置與下一回合必須重新產生。
- 在敵方 AI 自己使用亂數之前先消耗此門檻，不能把全部門檻預先批次擲完。
- renderer 只讀保存值；不得因畫面更新頻率或輸入裝置增加亂數消耗。
- 敵人命令可見性採行動者智力乘被檢視者等級、整數除三後嚴格大於保存門檻。
  五種標籤／圖示參數另見命令面板證據，不因本規格自動授權整個 UI。
- 保留排序擲骰與本門檻擲骰的不同用途；不修改排序公式。
- 不擴充存檔格式；戰鬥中斷保存若未受既有契約涵蓋，另列待決策。

不可僅憑迴圈片段就對所有空槽增加擲骰。

重複入口、取消不變及下一回合重設；同一輸入鏈的亂數序列由 dosgolem 核對。
正式規則與 UI 測試、正常 GUI 遭遇及戰鬥各抽測；舊固定種子截圖預期可能改變，
先核對原版亂數順序再重生，不為保留舊畫面移動擲骰位置。

0x1FAC1 原始回跳，在 0x1F16A 設測試返回出口；連續三次均保持門檻與排序位置，
亂數出口一旦被呼叫即失敗。首次採正規化段位址導致向後 near JMP 的 IP 下溢，

重跑整批 panels 通過（0.377 秒）。此為控制流抽樣，不代替正常取消 UI 驗證。

範圍、擲骰時序、倒下／空位、敵方 AI 前順序及取消保持皆有最小充分證據。
正式一次性狀態應隸屬 Round 的排序位置，於新回合重設；不可由 BeginTurn 重設，
因為目標及移動取消都呼叫 BeginTurn。BeginPlanning／EndTurn／AdvanceToParty
經過同一位置時必須共用已進入標記，避免重複擲骰。
據此升 READY，不更動存檔格式、不授權未證實的加速或 AI 行為；實作後仍須完成
既定測試與正常玩家路徑驗收。
